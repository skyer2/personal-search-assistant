# Root Cause Report — Research Process Observability and Insight Recovery

Date: 2026-09-23
Baseline: `429f6c47f3def564b8b555b7635d13393fb7617d`

This report was completed before implementation, as required by the SDD.

| Area | File / function | Current behavior | Root cause |
|---|---|---|---|
| Plan | `app/observability/semantic_events.py::plan_event_attributes`; `app/observability/journal.py::summarize_trace`; `frontend/src/components/TraceViewer.tsx` Plan tab | The plan event exposes task count and task IDs; the UI renders IDs and brief coverage. Internal `ResearchTaskSpec` has some task details, but they are not carried into semantic events. | The runtime plan contract and observability plan projection are separate; the UI consumes only the compressed event projection. |
| Worker state | `app/observability/semantic_events.py::worker_event_attributes`; `app/observability/journal.py::_coalesce_worker_row`; Trace Viewer Worker table | The UI shows status, execution status, result status, fail reason, budget fields and last tool error side by side. Evidence and artifact identifiers are not split. | The runtime correctly records several independent dimensions, but there is no presentation DTO mapping them into one outcome, one stop reason, a readable budget, and separate Evidence/Artifact lists. |
| Coverage | `app/research/coverage/judge.py::judge_coverage`; `app/research/runtime/runner.py::node_coverage_judge`; `app/observability/journal.py::summarize_trace` | Coverage computes direct binding, evidence, source independence, primary, freshness and conflict checks. The event contains per-question data, but the journal keeps only status/sufficiency/missing/conflicts/reason and drops most question fields; the UI therefore shows little explanation. | Decision data is richer than the event-summary projection, and the UI's table is not a question-level explanation view. |
| Repair | `app/research/supervisor/agent.py::_task` / `fallback_action`; `app/research/runtime/runner.py` repair dispatch and coverage | A bounded task is created from a Coverage gap and a Coverage delta is calculated, but before/after context is distributed across plan, worker and coverage events. | There is no unified repair record joining its reason, requested evidence, budget, added evidence, and after-coverage result. |
| Insight | `app/research/delivery/insight_synthesis.py::build_insight_synthesis`; `app/research/delivery/insights.py::build_insight_layer`; `app/research/runtime/runner.py` synthesis stage | The runner has two Insight contracts. The full builder creates claim groups/signals/cards/bindings but never appends a `MechanismAssessment`; the simpler layer requires two findings grouped by criterion. UI metrics read the simpler layer. | The active Insight metric comes from a legacy heuristic; the canonical builder's mechanisms list is always empty, and no gate stops analytical synthesis when insight is absent. |
| Provider failure | `app/research/execution/synthesis_executor.py::_extract_response_content` / `_analyze_response` | Unsupported response shape and cleaner-removed content are distinguished, but raw empty responses all become `provider_empty_content`. | HTTP, stream completion, finish reason/content-filter and structured parse metadata are not normalized into the requested failure taxonomy. |
| Recovery | `app/research/delivery/answer_contract.py::compile_deterministic_answer` / `render_final_answer`; `app/research/runtime/runner.py` recovery branch | Recovery picks validated claim text per question and binds evidence, but presentation remains a compact evidence-first answer with little signal/mechanism synthesis. | The fallback contract has no evidence-grounded signal/mechanism model or strict semantic review stage; answer completeness is treated as sufficient semantic quality. |
| Fallback PASS | `app/research/runtime/runner.py::node_quality_gate`; `app/research/quality/gate.py`; `app/research/domain/completion.py::evaluate_completion` | A complete evidence-bound recovery can pass when answerability, citations, and report-quality checks pass. | Quality evaluation has no stricter fallback-specific criteria for insight presence, evidence-dump detection, relevance, distinct sections or reasonable citation count. |
| Claim/Evidence binding | `app/research/claims/admission.py`; `app/research/delivery/insight_synthesis.py::_binding`; `app/research/delivery/view_builder.py` | Claims are checked for valid Evidence IDs and question lineage; the view maps bound Evidence to citations. No explicit relevance relation/score gates body use; broad evidence sets can produce long citation strings. | Binding is referential, not semantic: there is no deterministic `direct_support / supporting_context / counter_evidence / irrelevant` contract or top-three body citation cap. |
| Trace diagnosis | `app/observability/semantic.py::earliest_failure_origin`; `app/observability/journal.py::summarize_trace`; `frontend/src/components/TraceViewer.tsx` | A low-level earliest failure origin and per-event tables exist. The UI has no `RunDiagnosis` or causal chain from first quality degradation to final delivery. | Trace remains a collection of event projections; there is no cross-stage reducer that orders plan, worker, coverage, repair, insight, synthesis and quality outcomes into a human-readable diagnosis. |

## Implementation constraints derived from the root causes

- Preserve the existing LangGraph, worker count ceiling, WebSocket, memory and event protocol.
- Enrich semantic event attributes and trace projection rather than creating a parallel trace system.
- Keep outcome semantics deterministic; a provider fallback is visible and cannot bypass strict quality rules.
- Do not claim completion until offline suites and a real `.env` run verify the final code.
